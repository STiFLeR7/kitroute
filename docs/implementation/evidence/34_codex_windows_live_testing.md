# Codex Windows live test

Date: 6 October 2026. Tasks: P01 host entry, P03 automatic routing, and P04 setup lifecycle.
Branch: `feat/p01-foundation-discovery`. Base commit: `7bf96ded31daeb1771aebd8a02a59e9827f1e9d8`.
This report covers uncommitted changes after that commit.

The Windows Codex smoke test passed after a command fix. This result closes the earlier Windows hook command gap.
It does not complete the milestones for Fedora, runtime support, comparative evaluation, or the developer pilot.

## Environment and scope

The test used Windows 11 Home Single Language, build `26200`, PowerShell `7.6.6`, Node `24.11.0`, and Codex CLI `0.157.1`.
The native Codex app-server used `gpt-6-luna` with low reasoning effort. `codex login status` reported login through ChatGPT.
The model calls used that account. No separate API key was used.

The test used a temporary home, project, and Kitroute database. The project path contained spaces.
The test did not install Kitroute into the user's normal Codex configuration.
The temporary login copy was removed after the test. Credentials were not printed or added to the repository.

This is a Codex CLI and app-server result with ChatGPT sign-in.
It is not a test of this desktop chat or the ChatGPT web interface.
Kitroute currently implements Claude Code and Codex adapters. It does not implement a ChatGPT web adapter or an MCP server.
The [developer command reference](https://learn.chatgpt.com/docs/developer-commands) states that Codex CLI commands do not apply to ChatGPT web.

## Failure and correction

The original command began with a quoted Node executable path. PowerShell treated that path as an expression.
The native host reported `hook exited with code 1`. The hook emitted no context, and the model replied `NONE`.
A direct PowerShell run also failed with `ParserError` and `Unexpected token` for the quoted script path.

Codex on Windows needs the PowerShell call operator, `&`, before the quoted executable.
The corrected command generated by setup was:

```powershell
& "C:/Program Files/nodejs/node.exe" "D:/kitroute/bin/kitroute.mjs" hook --host codex --event UserPromptSubmit
```

`buildCommand` now adds `&` only for Codex on Windows. The Claude Code and Linux command forms remain the same.
Setup now registers Codex hooks on Windows. It still requires the host's normal hook review.

A new regression test executes a generated command through PowerShell with a script path that contains spaces.
It makes sure that arguments and the JSON input reach the script unchanged.
That test and the Windows registration test both failed before the correction. The full suite then passed all 161 tests.
No tests failed or skipped on Windows.

## Native host results

The test reviewed both generated hooks through the normal `/hooks` interface.
The app-server then reported `trusted` for `UserPromptSubmit` and `SessionStart`.
The test did not use `--dangerously-bypass-hook-trust` or manually write trust hashes.
The [hook documentation](https://learn.chatgpt.com/docs/hooks) describes this review requirement and the supported context output.

The test used the installed native protocol with `hooks/list`, `skills/list`, `thread/start`, and `turn/start`.
The native skill list included the matching skill, a disabled skill, and an explicit-only skill.
The test made its assertions against hook completion events. A model reply alone was not enough to pass.

| Case | Hook result | Whole hook duration |
| --- | --- | --- |
| Ordinary request | Matching guidance reached the model. | 442 ms |
| Repeated request in the same session | Hook completed with no repeated guidance. | 424 ms |
| Unrelated request in a new session | Hook completed with no guidance. | 478 ms |
| Request matching a disabled skill | Hook completed with no guidance. | 403 ms |
| Request matching an explicit-only skill | Hook completed with no guidance. | 456 ms |
| Request to follow selected instructions | Guidance arrived and the skill body marker appeared in the final reply. | 411 ms |

All six model turns completed. The startup hooks also completed without context in new sessions.
The first five cases used ordinary text without an explicit skill command.
The disabled skill used `enabled = false` in `[[skills.config]]`.
The explicit-only skill used `policy.allow_implicit_invocation: false` in `agents/openai.yaml`.

The final prompt was:

```text
Debug synthetic checkout failure. Follow the selected skill instructions. You can read its SKILL.md. Do not edit files.
```

The prompt did not name the skill or include its marker. The final reply was `KITROUTE_NATIVE_SKILL_8e91`.
That marker existed only in the synthetic skill body. This proves that the body instructions affected the reply in this run.
It does not prove a native skill-loading event or an improvement over Codex's existing skill selection.

Native `UserPromptSubmit` input included these keys:

```json
["session_id", "turn_id", "transcript_path", "cwd", "hook_event_name", "model", "permission_mode", "prompt"]
```

The output used `hookSpecificOutput.hookEventName` and `hookSpecificOutput.additionalContext`.
The context contained only the selected capability name, action, and target path.
The native notification called the event `userPromptSubmit`. The hook input and output used `UserPromptSubmit`.

## Setup, history, and cleanup

Setup preview returned the two planned Codex entries. Setup applied them, and a second preview returned no patches or conflicts.
The live test executed those exact generated commands after native review.
The regression suite also passed the package installation and reversible setup tests.

Codex skill-loading observation remains unknown. The test did not turn a reply marker into a claimed loading event.

Uninstall preview changed no bytes. Uninstall removed both owned entries and the setup manifest.

The temporary CLI sessions and app-server processes exited. The temporary `auth.json` copy was removed.

## Limits and next work

The package declares Node `>=24.21.0 <25`, but this machine ran `24.11.0`.
The passing smoke test does not settle that runtime mismatch. Fedora tests remain unrun.
Resume, compaction, plugin skill discovery, live MCP availability, and model comparisons remain outside this smoke test.
The six small cases do not satisfy P05 evaluation or the five-developer pilot.

The temporary home triggered a Codex daemon error because its socket path exceeded `SUN_LEN`.
The interactive review used the host's `--no-daemon` option. The live protocol tests used the app-server over standard input and output.
Codex also warned that it could not create helper aliases inside a temporary home. Neither warning prevented the successful hook runs.

The direct generated hooks took 403–478 ms for the prompt event in these runs.
An earlier wrapper probe took 3395 ms. These measurements include host shell startup and differ from Kitroute's internal worker deadline.
They do not establish a general latency guarantee.

Windows automatic guidance and reversible Codex setup pass this smoke test.
M1, M3, and M4 remain in progress until their remaining exit evidence exists.
